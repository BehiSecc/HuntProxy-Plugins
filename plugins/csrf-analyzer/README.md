# CSRFAnalyzer

CSRFAnalyzer requires `allow_state_change=true` because it repeats the captured
request. It independently tests token removal/mutation/duplication across form,
query, header, and nested JSON locations; Origin and Referer absence/cross-site behavior;
method and content-type controls; and optional cross-session token binding with
a second identity.

When a token is present, isolated Origin, Referer, content-type, and override
responses are diagnostic only. Findings require a combined token-removal probe
plus a stable rejected invalid-token control, avoiding claims based on requests
that still carry a valid token.

For one-time tokens, provide `fresh_token` with an in-scope acquisition URL,
a body regex whose first capture is the token, and its typed request location.
Each replay becomes a host-owned GET → POST workflow. Extracted values remain
internal and a missing token aborts before the state-changing request. Fresh-token
workflows run sequentially so concurrent acquisitions cannot invalidate each other.

The default scan compares a response fingerprint containing status, decoded and
canonicalized `Location`, and normalized body content. A mutation must agree with
the accepted baseline and its paired invalid-token control must be rejected or
materially different. This handles common POST/Redirect/GET endpoints whose `302`
responses have empty bodies. Without an independent read-back, these findings are
tentative because the differential proves request acceptance rather than durable
server state.

Legacy `success_markers` and `failure_markers` match the body and decoded response
headers, including `Location`. For precise matching, `success_predicate` supports
status codes, headers, redirect location, body text or regex, and JSON pointers.

For firm state confirmation, configure `readback` with a safe same-origin GET URL
and a response predicate. The analyzer runs submit → read-back sequentially after
every baseline and mutation. Predicate strings can contain `{counter}` so they can
verify the unique value generated by `per_request_values`. Read-back is optional;
the ordinary one-click differential scan remains the default.

The separate `browser_scan` action accepts a named managed cookie profile and
uses isolated Chromium to issue a token-removal top-level GET or cross-site form
POST from an isolated opaque cross-site document. It exercises real browser cookie
policy while leaving the fast semantic scan unchanged. Only reproducible delivery
of a matching managed-profile cookie is returned as an acceptance candidate,
never a finding: the cookie may not be authenticating and browser delivery still
needs an independent state read-back.
Unsupported methods and non-form POST bodies are rejected explicitly.

The analyzer reports precise failure reasons such as `transport_failed`,
`responses_differed`, `success_predicate_not_met`,
`readback_predicate_not_met`, and `negative_control_not_distinct`. It does not
automatically mutate multipart tokens. Browser mode currently covers form-compatible
GET/POST delivery from an opaque initiator; sibling-domain, client-side redirect,
and WebSocket chains remain separate specialized workflows.

`paired_cookie_tests` always use the explicit identity and token pair supplied by
the caller; the primary identity's `fresh_token` workflow does not replace it.

For non-idempotent fields such as a unique email address, `per_request_values`
can replace a typed body, query, or header value on every replay. Templates must
contain `{counter}`; they cannot target configured CSRF token names.
